# Контракт и границы подтверждения

## Источники

Для спорных мест использованы ответы администратора из `ВопросыИОтветы.txt`
и рабочие запросы из `v8_utils.groovy`. [API.md](Исходный_API.md) хранится
в пакете как исходная редакция. В частности, таблица `loading1c/new` в ней
предшествует уточнениям по `user`, `osname` и `makecopy`.

Для устройства пакета использована [документация библиотек OneScript](https://oscript.io/learn/libraries).
HTTP-конструктор сверен с
[исходником OneScript 2.1.0](https://github.com/EvilBeaver/OneScript/blob/v2.1.0/src/OneScript.StandardLibrary/Http/HttpConnectionContext.cs)
и [справкой HTTPСоединение](https://oscript.io/syntax/HTTPConnection):
HTTPS задаётся схемой URL, SSL-объект не передаётся, восьмой аргумент
управляет аутентификацией ОС.

## Соответствие методов

Корень по умолчанию: `https://ukm-web/ad/IT/IT_TechAdmin/hs/`.
Сначала проходит доменная HTTP-аутентификация, затем защищённый метод
проверяет токен. Клиент передаёт `token` в query для GET и в JSON для POST
по образцу рабочих запросов `GetInfobaseBlock`, `loading1c/status`,
`SetInfobaseBlock` и `loading1c/new`. Рабочий лог на варианте с заголовком
показал `code=5` на `GetInfobaseBlock`. Проверка исправления на агенте описана
в [ПРОВЕРКА.md](ПРОВЕРКА.md).

## Правила ответов

По контракту HTTP всегда 200; иной HTTP-код — ошибка веб-сервера/аутентификации.
Содержимое — JSON с `code`, `description`, `result`.
Числовой `0` и строка `"00.00"` — успех; совместимая строка `"0"` также принимается.
Все остальные коды, включая `00.01` и `00.12`, — ошибки.
Для успеха требуется наличие `result`. Ответ HTML со статусом HTTP 200
не считается успехом.

Коды передаются в исключение вместе с описанием сервера. Полные таблицы кодов
для каждого адреса находятся в [снимке исходного API](Исходный_API.md).
Частые примеры: `5–8` у защищённых Objects1C-методов — отсутствие, неверный токен
или недостаточные права; `12` у KillSession — таймаут удаления сеанса.
Числовые коды разных методов нельзя интерпретировать как общий справочник.

## Подтверждено рабочими примерами пользователя

- Восстановление: `sourceinfobase`, `targetinfobase`, `makecopy`;
  GUID приходит строкой непосредственно в `result`.
- Статус: параметр `guid`; `result=0` — готово, `-1` — ошибка,
  `1` — выполняется, `2` — приостановлено. Есть `update_date`.
- Блокировка: `Objects1C/SetInfobaseBlock`, поля `SessionsLockEnabled`,
  `LockBeginTime`, `LockEndTime`, `SessionStartPermissionCode`,
  `LockMessage`, `LockScheduledJobs`, секрет из Jenkins credentials.
- Формат дат рабочего `test_lock.txt` — `yyyy-MM-ddTHH:mm:ss` без зоны.

## Уточнения администратора

- `makecopy` — булево. Свежая копия с продуктива дифференциальная, с остальных
  источников полная. Файл временный, его удаляет оркестратор.
- `user` — пользователь ИБ. `osname` задаёт для него аутентификацию ОС.
  Пользователи источника сохраняются. Автоматический сброс пароля возможен
  только для указанного `user`. Конфликт уже назначенной ОС-учётки пока обсуждается.
- `forcecreate` создаёт отсутствующую ИБ/БД. Для существующей базы параметр
  можно пропустить. Источник можно найти через `GetInfobases`, доступ определяется
  проектом, командой и видом ИБ.
- Восстановления на одной СУБД идут последовательно. При `result=2` заявка
  ждёт проверки администраторов БД, клиент продолжает опрос раз в минуту.
- При восстановлении оркестратор сам блокирует и разблокирует базу, очищает кэш.
  `SetInfobaseBlock` запрещает вход, открытые сеансы остаются. Для монопольного
  обновления нужна операция завершения сеансов **и соединений**,
  её контракт ещё обсуждается. `CacheReset` предназначен для оркестратора.
- `run1c/generate` предназначен для продуктивного контура.

## Что требует живой проверки

1. Чтение блокировки с токеном и эмуляция восстановления под УЗ Jenkins-агента.
2. Точная сигнатура новой операции завершения сеансов и соединений.
3. Сопоставление времени блокировки на агенте и сервере.
4. Права токена на чтение, блокировку и восстановление.
5. Для отдельных задач вне этого пайплайна остаются открыты HTTP-типы проектных
   справочников, параметры `GetBDSize` и расхождение `user/osuser` в `run1c/generate`.

## Границы этого этапа

Клиент не собирает конфигурацию, не запускает 1С, не создаёт пользователей,
не отправляет Telegram/RabbitMQ, не выполняет скрытый CacheReset,
не отменяет заявку и не восстанавливает прежние параметры блокировки автоматически.
Это обязанности следующих скриптов и пайплайна, которые будут использовать
данную библиотеку и текущие рабочие наработки.
