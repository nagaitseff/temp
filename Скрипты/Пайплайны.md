Пайплайны Jenkins (ERP)

## Назначение

Контекст проекта для разработки и переработки Jenkins-пайплайнов 1С:ERP.
Новый пайплайн «восстановление аналитической базы + накат сборки» строится
на библиотеке mechel 2.0 (см. Промпт №1 «Библиотека»). Правило проекта:
точность и честность важнее скорости — всё проверять, моделировать без ошибок,
документация сразу в markdown, по существу, с примерами.

## Сценарий нового пайплайна (что строим)

Единый пайплайн «аналитическая база»: выбрать ветку и базу-источник → восстановить
базу через API оркестратора → накатить сборку из ветки → открыть доступ аналитику.
Параметры: ветка, база-источник, целевая база, флаги (смок-тесты, FirstMaintence, отладка).

## Цепочка стейджей нового пайплайна

1. **Init** — параметры, валидация ветки (регэксп: feature/0000, fix/0000, develop, master, hotfix/0000, release/2.5.26.14), определение «что менять» через `ОпределитьЧтоМенятьМеждуВетками` (файлы-флаги `create_cf.txt`/`create_ext.txt`, формат 1/0 — как в существующих джобах); `currentBuild.displayName` = имя ветки
2. **Restore DB** — `АПИКлиент.ЗапуститьВосстановление(targetinfobase, sourceinfobase, makecopy, osname, comment)` → ГУИД → `ОжидатьЗавершенияВосстановления` (интервал 1 мин, таймаут 2 часа); RabbitMQ-статусы BEGIN → «Восстанавливаю базу» → «В процессе...» → «Восстановление завершено»
3. **Первичная настройка** (опционально, галочка) — osname в заявке уже даёт доменную УЗ; при необходимости — FirstMaintence.epf с параметрами из формы запуска (имя/пароль пользователя — параметры)
4. **Lock + kill sessions** — API: `УстановитьБлокировку` + `ПолучитьСеансыБазы` → `ЗавершитьСеансыБазы` (исключения) → проверка «сеансов не осталось» (замена LockUnlockBase)
5. **Load CF** — конфигуратор, `ЗагрузитьКонфигурациюИзФайла` + `ОбновитьКонфигурациюБазыДанныхНаСервере`; файл — из артефактов `\\ukm-sapp108\artifacts\<ветка>\`, копия под `<база>.cf` как в рабочем LoadCf
6. **Load Mechel** — конфигуратор, `ЗагрузитьРасширениеИзФайла(путь, имя, Истина)` (замена существующего)
7. **Install new EXT** — предприятие (только если «новое расширение»), обработка InstallExtension.epf, `БезопасныйРежим = Ложь`, запуск с проверкой кода возврата
8. **Start & Update** — предприятие, `ЗапуститьОбновлениеИнформационнойБазы;ЗавершитьРаботуСистемы;` + /UC + ЗакрытьПредприятие.epf; **проверка кода возврата** (в легаси не проверяется — исправляем)
9. **Unlock + CacheReset** — API: `СброситьКэш` + `СнятьБлокировку`; в `post { always }` гарантия разблокировки
10. **SmokeTests** (опционально, по умолчанию выключен) — предприятие, `RunUnitTests=...yaxunit_smoke.json`; allure-отчёт в `post always`; при падении статус UNSTABLE
11. **RabbitMQ-статусы** на каждом шаге: формат `{"timestamp", "base_GUID", "project", "status"}`; финал SUCCESS; телеграм в новом пайплайне не используется

## Конвенции (переносим из рабочих пайплайнов)

- Гейты через файлы-флаги: `1`/`0`, проверка существования файла
- Артефакты по ветке: `\\ukm-sapp108\artifacts\<ветка>\`
- Паттерн `catchError(message, buildResult, stageResult)` — стейдж падает красным, диагностика продолжает собираться
- `post { always }`: разблокировка, allure, очистка; `DEBUG_BUILD_1C` отключает очистку временных каталогов
- `disableConcurrentBuilds()` для пайплайнов с базами
- Паузы между каскадными запусками — 1 минута
- Комментарий заявки: `Jenkins: job=<имя> #<сборка> | <автор>`

## Известные проблемы легаси (не терять, чинить в новых, старое не трогать)

- `ТриМинуты = 1800; Приостановить(...)` — Приостановить принимает миллисекунды: пауза 1,8 сек вместо 3 мин (LoadCf, LoadExtension, UploadOriginalSupplyCfFile)
- StartAndUpdate не проверяет код возврата предприятия — «зелёный» пайплайн при упавшем обновлении
- Пароль из констант попадает в командную строку процесса 1cv8.exe (UploadOriginalSupplyCfFile, FirstMaintence) — видно в диспетчере задач
- Абсолютные пути зашиты: `C:\OneScript_2\lib\vanessa-runner\epf\ЗакрытьПредприятие.epf`, `C:\ERP_Project\CF_Supply\`
- Парсинг булевых через `ВРег(...) = "ИСТИНА"` — заменяем на `ВБулево`
- `СоздатьНужныйКаталог` копипастится в скриптах — в библиотеке отсутствует
- Токен/константы из ConstantsForJobs.json — переходим на параметры пайплайна и Jenkins credentials
- Проверка изменений по времени (`git log --since`) — заменяем на дифф веток `git diff --name-only origin/<база>...origin/<ветка>` + фильтр `src/cf` / `src/cfe`

## Принятые решения

- Smoke-тесты после разблокировки (конвенция всех существующих пайплайнов), статус UNSTABLE при падении
- osname в заявке на восстановление — основной путь доступа аналитика; FirstMaintence — опциональный стейдж, имя сохраняется
- Доп. расширение: имя и полный путь к cfe — параметры пайплайна
- База-источник — задаётся именем из формы запуска
- Токен — из Jenkins credentials
- Ветки: feature/0000, fix/0000, develop, master, hotfix/0000, release/X.X.X.X
- Легаси-джобы остаются как есть; новый пайплайн — на mechel 2.0; в перспективе все пайплайны приводим к единому стилю (шаги, обработка ошибок, логирование)

## Порядок работ

1. Сверить и принять Промпт №1 «Библиотека» и этот документ
2. Пересобрать библиотеку mechel 2.0 с правками из живого лога (update_date, makecopy строкой, опрос с параметрами) — одним архивом вместе с промптами

5. Написать os-скрипты нового пайплайна (LoadCf, LoadExtension два режима, StartAndUpdate с проверкой, InstallExtension.epf, CheckChangesInGitBranch)
6. Собрать Jenkinsfile нового пайплайна по цепочке стейджей выше
7. Отладка на стенде: сначала `test=1`, потом реальное восстановление на тестовую базу
