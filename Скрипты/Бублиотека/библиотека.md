Библиотека mechel 2.0
Назначение
Библиотека oscript mechel версии 2.0.0 — общий слой для os-скриптов Jenkins-пайплайнов проекта ERP. Состоит из:

новых модулей и классов (2.0) — пишутся с нуля, покрывают работу с API оркестратора «1С:Администрирование и эксплуатация» и служебную логику пайплайна;
легаси-модуля — существующий ОбщийМодуль.os, который остаётся без единой правки, его используют старые скрипты.
Требование пользователя: точность и честность важнее скорости. Всё проверять, моделировать без ошибок, покрывать тестами, документация — сразу в markdown, по существу, с примерами, без лишних описаний — «просто понятно и чтобы сразу можно было применить».

Сверенные факты API (источник: API.md + живой лог)
Общие правила
Точка входа: https://ukm-web/ad/IT/IT_TechAdmin/hs/ (зашита в класс по умолчанию, переопределяется конструктором).
Аутентификация: доменная (УЗ, под которой работает процесс — агент Jenkins). Явная учётка — опция конструктора.
Все ответы — HTTP 200 с JSON: {"code", "description", "result"}. code — число (0) или строка формата DD.DD ("00.00") — проверять оба варианта.
Токен — обязательный параметр большинства методов, передаётся в порядке поиска: query → тело → заголовки. Токен берётся из Jenkins credentials.
Формат идентификации базы: СЕРВЕР:ПОРТ|ИмяБазы, пример из живого лога: UKM-SAPP123:8541|ERP_KGOK_RELEASE_DRAFT.

Подтверждено живым логом (any_base_restore)
Ответ /new: ГУИД задачи — строкой прямо в result: {"code": "00.00", "description": "", "result": "4c401c09-..."}.
Ответ /status: содержит update_date вида 2026-11-18T09:43:04 — логировать при опросе.
makecopy передаётся строкой '1'.
Комментарий в заявке: 'Jenkins: job=any_base_restore_API #2144 | Мадьяров Тимур Тимурович' — формат Jenkins: job=<имя> #<сборка> | <автор>.
RabbitMQ-статусы: {"timestamp", "base_GUID", "project", "status"} со статусами BEGIN → «Восстанавливаю базу» → «В процессе...» → «Восстановление завершено» → «Сброс пароля не требуется» → SUCCESS.
Опрос статуса: интервал 1 минута, таймаут 2 часа (значения по умолчанию, параметризуемые).
Восстановление по этапам из API.md: оркестратор сам блокирует базу, завершает сеансы и меняет пароль обезличенного администратора (шаг 14) — наш logpassERP после восстановления может не подойти.
Публичный интерфейс
Класс АПИКлиент
Конструкторы: Новый АПИКлиент() — точка входа по умолчанию + доменная аутентификация; Новый АПИКлиент(Адрес, Логин, Пароль) — явная учётка. Токен задаётся отдельно (из credentials), в URL и лог не попадает, если передаётся телом.

Методы: ПолучитьАгентов, ПолучитьКластеры(Агент), ПолучитьИнфобазы(...), ПолучитьСеансыКластера(Кластер), ПолучитьСеансыБазы(...) (фильтр на стороне клиента), ПолучитьПользователейБазы(Инфобаза), ПолучитьБлокировку(Инфобаза), УстановитьБлокировку(Инфобаза, Параметры), СнятьБлокировку(...), ЗавершитьСеанс(НомерСеанса, Инфобаза), ЗавершитьСеансыБазы(...) (с исключениями и проверкой «не осталось ли лишних»), СброситьКэш(Инфобаза), ЗапуститьВосстановление(...), СтатусВосстановления(Гуид) (с разбором update_date), ОжидатьЗавершенияВосстановления(Гуид, Интервал, Таймаут), УстановитьОбслуживание/ПолучитьОбслуживание, ЗавершитьПроцесс.

Транспорт: HTTPСоединение из движка (без oint — снимается зависимость от его версии). GET-методы без токена вызываются без него (сверено: у них токена нет вовсе).

Модуль АПИСлужебный (чистые функции, без сети — тестируются изолированно)
Даты в ISO (2026-11-18T10:00:00, без таймзоны), разбор code (число/строка DD.DD), сборка query-параметров, разбор строки базы СЕРВЕР:ПОРТ|Имя, разбор адреса точки входа, фильтрация сеансов по базе, разбор result статуса восстановления.

Правила качества
Легаси-модуль не изменяется ни на символ.
Вся логика, доступная тестированию без сети, — в АПИСлужебный; класс — только транспорт и сборка вызовов.
Тесты: oscript #Использовать asserts; при провале — ненулевой код выхода. Покрыть: конвертер дат, разбор code, булевы, сборку URL, разбор адреса (включая ukm-web), фильтрацию сеансов, определение «что собирать», конструктор класса.
Никаких выдуманных фактов: если поле API не подтверждено — пометить TODO: сверить.
Ошибки API — человекочитаемые, без утечки токена в сообщения и логи.
Документация — README.md с установкой, конструктором, примером на каждый метод, таблицей кодов ошибок и разделом «что осталось сверить».
Принятые решения
Токен — из Jenkins credentials (пользователь подтвердил).
Дополнительные методы API — добавить все (решение пользователя).
FirstMaintence: имя сохраняется; «самый лучший вариант» = osname в заявке на восстановление (доменная УЗ приходит сама) + обработка как опциональный стейдж с параметрами из формы запуска (имя/пароль пользователя — параметры, не зашитые значения).
Обработка FirstMaintence делает: перезапись пользователей Разработчик/Аналитик (полные права, пароль), заголовок «STAGING …», перевод кролика в тестовый контур erp_staging_test.
Расширение доп.: имя и полный путь к cfe — параметры пайплайна (решение пользователя).
Открытые вопросы (не блокируют, помечены в коде)
Сброс пароля админа после восстановления (шаг 14 этапов /new): когда требуется и как получать новый пароль — не решено. В живом логе прошёл как «Сброс пароля не требуется».
Имена полей сеансов в /GetSessions — в API.md описан только тип «JSON». Живой ответ из ночной джобы (стейдж Lock & Kick) закроет.
/run1c/generate — расхождение внутри API.md: поле user в таблице против osuser в кодах ошибок; обязательный appname. Не использовать до выяснения.
Формат ISO-дат — документ не даёт примера; принято 2026-11-18T10:00:00, сверить по живому запросу.
Версии зависимостей (oint, messenger) сверить по каталогам C:\OneScript_2\lib\<пакет>\packagedef — opm list на ноде падает на прокси.
